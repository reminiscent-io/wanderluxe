Date & Time Range Picker for a Luxury Travel App

Overview & Requirements

For a luxury travel booking form, an ideal date-time range picker must meet several strict requirements:
	•	Range Selection (Start & End Dates): Users should select a start and end date in a single UI flow (e.g. by highlighting a range on a calendar) ￼.
	•	Time Inputs for Start/End: It should allow picking start and end times (hour/minute, with AM/PM or 24h format) alongside the dates ￼ ￼.
	•	Mobile-Friendly Modal UX: On small screens, the picker needs to behave like a modal or drawer – centered or full-screen with a backdrop – to avoid off-screen popovers and improve touch usability.
	•	Desktop Usability: On desktop, it should still behave elegantly (e.g. as a dropdown/popover) without regressing user experience.
	•	Radix/Shadcn Integration: The component must work inside an existing Radix Dialog (modal) without issues, and align with the Shadcn UI framework (which uses Radix Primitives + Tailwind).
	•	React Hook Form Compatibility: It should integrate smoothly with RHF, ideally via a controlled component or using RHF’s Controller, preserving form state and validation.
	•	Luxury Aesthetics: The styling should be minimal, refined, and easy to theme to a sand/earth tone palette – matching a high-end design aesthetic. A Tailwind + Shadcn based solution is preferred for consistency.

Installation Steps

If you’re already using Shadcn UI in your project, adding this component is very straightforward:
	1.	Import via Shadcn CLI: If you have the Shadcn CLI, you can install all the date-time picker components in seconds. Run the following command, which pulls the component registry JSON:

npx shadcn add https://date-time-range-picker.vercel.app/r/date-time-range-picker.json

This will import the DateTimeRangePicker and its related sub-components (calendar, inputs, etc.) into your project, with the proper file structure and styles ￼.

	2.	Manual Install (Alternative): If not using the CLI, you can manually copy the component files from the GitHub repo. Make sure to include all necessary parts (likely components for Calendar, DateInput, TimeInput, and the composite Range picker). Place them in your project’s components directory. The main file to include is often named something like DateTimeRangePicker.tsx (along with any hook or util files, e.g. date utils using date-fns if required).
	3.	Dependencies: Ensure you have required date libraries. This picker uses date-fns for date utilities (as Shadcn’s Calendar does). If not already in your package, install date-fns. Also ensure Radix UI and Tailwind are configured (which they should be in a Shadcn setup). For time parsing/formatting (AM/PM), the code likely leverages date-fns or native Date methods, so no heavy moment.js needed.
	4.	Style Configuration: The components come with Tailwind classes for styling. Verify that your Tailwind config includes the shadcn preset or equivalent, so that things like bg-popover or text-primary classes resolve to your theme’s colors. You might adjust the theme to a custom palette (sand/earth tones) by editing your Tailwind config (e.g. extending colors or setting CSS variables for --background etc.). The default should already be neutral and elegant. Minor refinements like adding a subtle transition or tweaking spacing can be done by editing the JSX or Tailwind classes in the component files.

Integration & Usage

Once installed, you can use the new <DateTimeRangePicker> component as a drop-in replacement for your existing DateTimeRangeField. It is designed to work as a controlled input. Below is an example of integrating it within a React Hook Form, using a Controller (assuming your form is already set up with RHF):

import { Controller, useForm } from "react-hook-form";
import { DateTimeRangePicker } from "@/components/ui/DateTimeRangePicker";  // path where you added it

function BookingForm() {
  const { control, handleSubmit } = useForm({
    defaultValues: {
      travelDates: {
        start: null,
        end: null,
      },
    },
  });

  const onSubmit = data => {
    console.log("Selected range:", data.travelDates);
    // ... submit or further process
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      {/* Other form fields... */}

      <Controller
        name="travelDates"
        control={control}
        render={({ field }) => (
          <DateTimeRangePicker
            {...field}
            // The field.value is an object { start: Date | null, end: Date | null }
            // The component will call field.onChange with an updated {start, end} object:
            onChange={(newRange) => field.onChange(newRange)}
            // You can pass additional props for display:
            placeholder="Select travel dates"
            hideWeekdays={false}  // example prop, depending on the component’s API
            className="w-full"
          />
        )}
      />

      {/* Optionally, you can display validation errors or hints */}
      {/* ... */}

      <button type="submit" className="btn-primary mt-4">Submit</button>
    </form>
  );
}

In the code above, the <DateTimeRangePicker> will handle its own open/close state and UI internally. When the user picks a start date/time and end date/time, it will call the provided onChange with the new range value (for example, { start: Date, end: Date }). We tie that to React Hook Form by passing field.onChange. The field.value is also passed in so the picker can display the current selection (or nothing if none). This way, RHF retains the form state and you can easily validate that travelDates.start and travelDates.end are set.

Modal Behavior on Mobile: By default, this component uses a Radix Popover for the dropdown calendar. To ensure a true “modal” feel on mobile devices, you have a couple of options:
	•	Use Popover.modal prop: The included Popover from Radix can be set to modal={true} to prevent background interaction. This is highly recommended when embedding in a Dialog, and is likely enabled in the provided code by default ￼. It ensures that tapping the calendar or time inputs doesn’t cause inadvertent closes.
	•	Switch to Dialog on small screens: You can detect the screen size (via CSS media queries or a small React hook) and conditionally render a Radix Dialog containing the date-time picker instead of a Popover. For example, on screens below a certain width, use a full-screen Dialog that shows the calendar and time inputs centered. This approach – a dropdown on desktop and a drawer/modal on mobile – is a known responsive pattern in Shadcn UI ￼. The component’s composable design allows you to implement this without rewriting the picker: you’d wrap the calendar part in a Dialog.Content for mobile view. The result is a focused, distraction-free date/time selector on mobile (no overflowing off the screen), akin to a native picker experience.

A11y and UX Considerations
	•	Accessibility: The recommended picker uses Radix primitives, meaning it follows WAI-ARIA best practices for dialogs, popovers, and focus management. Users can navigate the calendar via keyboard (arrow keys, etc.) and the time fields via keyboard or native inputs. Ensure to label the fields appropriately (the component likely already has labels or aria-labels for start/end).
	•	No Timezone Logic: This solution does not impose any timezone handling – it works with JavaScript Date objects or strings and leaves timezone interpretation up to you. By default, it will use the local time (or whatever Date you pass in). This meets the requirement of avoiding complex TZ logic. (It does support timezone features if needed, but you can simply ignore that and treat all dates as local times ￼.)
	•	Preset Ranges: The component also supports preset ranges (common ranges like “Next 7 days”, “Next 30 days”) which can be handy for quick selection ￼. You can configure these presets or disable them. This might enhance UX for a travel app (e.g. quick buttons for “Weekend” or similar).
	•	Animations & Styling: Out of the box, the picker transitions are subtle and polished (Radix uses hardware-accelerated animations for dialogs/popovers). If you want to further enhance, you can add Tailwind classes for transition durations or use Framer Motion for a bespoke animation. For example, on mobile you might animate the drawer sliding up. Since all elements are under your control (JSX code available), you can add these enhancements without breaking the core functionality.
